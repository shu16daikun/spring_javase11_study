## 0. 前提と用語

* **モジュール**

  * `main_app`（本体アプリ）
  * `my_login`（ログイン/ユーザー/権限基盤）
  * `my_util`（MyType/RoleUtil/ZeroPadding/IdBridge/ReplaceNull 等）
  * `my_exception`（MyException/MyRuntimeException/ErrorCode/ErrorUtil）
  * `my_fragment`（共通フロント資産 `/psfm`）
* **依存方針（Spring / JPMS 無効運用）**

  * `module-info.java` は作成しない（**JPMS無効**）。クラスパス型 Spring Boot 前提。
  * モジュール間依存は **Mavenのpom**（jar依存）で管理。**公開契約は api/* のみ**参照可。
  * 依存解決は **コンポーネントスキャン**（`@SpringBootApplication(scanBasePackages=...)`）。必要に応じて `@EntityScan` / `@EnableJpaRepositories` で境界指定。
  * JVM の `--add-opens` は不要（反射は Spring 標準に委譲）。
* **責務の主軸**

  * Controller：薄く（I/O と遷移決定のみ）
  * Service：ユースケース・取引境界（`@Transactional`）・メソッド認可（`@PreAuthorize`）
  * Repository：各コンポーネント内に閉じる（**他モジュールの Entity/Repo 直参照禁止**／**Service API 越し**）
* **DTO 方針**

  * ViewDto：`fromEntity()` のみ（出力整形/擬似ID化）。**入力に使わない**
  * Form：`toInputDto()` / `fromViewDto()`（**Controllerのみ使用可**）
  * InputDto：Service内で `toEntity()`（private）。認可/暗号化/関連解決もここで最終確定

## 14. Getter / Setter 規約（Java 21 / Spring MVC / Thymeleaf / Lombok）

> 方針: **フォーム以外は不変**。外部入力は Form に限定。AOP 対象の実装クラスは **public 非final** を維持。

### 0) 共通原則

* **公開 Setter は最小限**（外部入力は Form のみ）。
* **不変（immutable）を基本**：`ViewDto` と `InputDto` は **record（Java 21）** を第一候補（Lombok不要）。
* **Entity はドメイン操作メソッド**で状態変更（`public setXxx` 原則禁止）。JPA のため **デフォルトコンストラクタ（PROTECTED）** は必須。
* **層の責務**：

  * **Form**：Web バインディング用。`public` getter/setter 必須。
  * **InputDto**：ユースケース入力。**record** を推奨（不変）。
  * **ViewDto**：画面表示専用。**record** を推奨（不変）。
  * **Entity**：永続化対象。Setter は `protected/package-private`。変更は意味のあるメソッド経由。

### 1) Entity（JPA）

* フィールド: `private`／`@Getter`（公開）
* Setter: **原則なし**。やむを得ない場合は `@Setter(AccessLevel.PROTECTED)` か フィールドを `protected/package-private`。
* コンストラクタ: `@NoArgsConstructor(access = AccessLevel.PROTECTED)`（JPA）＋業務用 `public` コンストラクタ/ファクトリ。
* 変更は **意図のあるメソッド** で行う（例: `changePassword(...)`）。
* `@EqualsAndHashCode`: IDベースにする場合は `onlyExplicitlyIncluded=true` で `id` のみを含める。

### 2) ViewDto（画面表示：不変）

* 形式: **record** を推奨（例: `public record PasswordSetViewDto(String username) { }`）。
* 付加ロジックが必要なら `static fromEntity(...)` を定義（従来方針を踏襲）。
* Jackson/Thymeleaf でそのまま利用可。

### 3) InputDto（ユースケース入力：不変）

* 形式: **record** を推奨（例: `public record PasswordSetInputDto(String password, String passwordCheck) { }`）。
* Bean Validation はレコードコンポーネントに付与可（例: `public record X(@NotBlank String a) {}`）。
* `Form` からの変換は `Form#toInputDto()` または `Assembler/Mapper` で実施。

### 4) Form（Web バインド：可変）

* フィールド: `private`（**final 禁止**）
* Getter/Setter: **public**（Spring バインディングのため必須）
* デフォルトコンストラクタ: **必須** (`@NoArgsConstructor`)
* バリデーション: `@NotBlank` 等 or カスタム `Validator`

### 5) 追加ルール

* ``** は禁止**（特に Entity）。
* 機密情報の Getter には必要に応じて `@JsonIgnore`（API化時の安全網）。
* 命名: `XxxForm` / `XxxInputDto` / `XxxViewDto`。変換は `Assembler/Mapper` へ集約。
* MapStruct を使う場合は **コンストラクタ/record マッピング** を基本に（Setter不要）。

### 6) チートシート

* **Entity**: `@Getter`、`@NoArgsConstructor(PROTECTED)`、Setter無し（必要時 PROTECTED）／変更はメソッド。
* **ViewDto**: **record**（不変）／`fromEntity(...)` で生成も可。
* **InputDto**: **record**（不変）／`Form#toInputDto()` で生成。
* **Form**: `@Getter @Setter @NoArgsConstructor`／`final` 禁止。

> 備考: AOP 対象（`@Service/@Repository/@Component`）の実装クラスは **public 非final**（final 禁止）。

## 15. ID / DTO バリデーション規約（2025-10-18 追加）

### 1) ViewId の検証方針

* ViewId のフォーマットが未確定／共有不能な間は、api/dto 側で `@Pattern` は付けない。
* 代わりに **Service 入口で ****``**** を必ず通す**。
* 不正形式は **Bridge 層で例外化**し、`@ControllerAdvice` で画面エラーへマッピングする。

### 2) フォーマット確定後の厳格化

* 接頭辞・桁数が確定したら、regex を定数化（`IdConstants/IdRegex` 等）。 例）

  ```java
  public final class IdRegex { public static final String KQ_VIEW = "^KQ\d{8}$"; }
  ```
* `api/dto` の該当フィールドに `@Pattern(regexp = IdRegex.KQ_VIEW)` を付与して **早期バリデーション**。
* それでも最終責務は **IdBridge** 側に残し、**二重防御** とする（Bridge は常に厳格）。

### 3) DTO の役割

* DTO は **record（不変）** を推奨。Bean Validation は **存在・長さなどの軽量検証** を主担当。
* `null`/空文字の正規化は **record のコンパクトコンストラクタ** で行う。
* 認可（`@PreAuthorize`）は DTO へ付けない。Controller/Service に集約。

### 4) IdBridge の責務

* **ViewId ↔ EntityId の変換・検証を一元化**（ZeroPadding／接頭辞／桁数チェック）。
* 変換失敗時は `** + **` を投げ、画面/API で統一ハンドリング。

### 5) 実装メモ

* 既知の ViewId 形式（例：KQ/SA/CH）が doc で確定済みなら、`@Pattern` を積極適用。
* 未確定なら `@NotBlank` のみに留め、**Bridge 検証に一本化**。

## 16. 多重防衛（Validation / Authorization / Consistency）規約（2025-10-18 追加）

### 0) Frontend（validation.js / controller.js）

* 必須/長さ/簡易正規表現など **即時UXの軽量検証のみ** を実施。認可や整合は扱わない。
* `regex`・最小/最大は **util_module の定数** を参照（ビルド生成 or 配信）。

### 1) Controller 層（Form/BindingResult）

* `@Valid` + カスタム Validator で **画面入力の妥当性を確定**（クロスフィールドも含む）。
* エラー時は **テンプレ返し**（422相当）。`BindingResult` + `errorMessage` で表示。
* **Form→InputDto 変換のみ** 行う。`IdBridge`/認可は呼び先（Service）に委譲。

### 2) Service 層（ユースケース境界：最終防衛）

* `IdBridge.toEntityId(...)` を **必ず通す**（ViewId 検証の最終責務）。
* `@PreAuthorize` による **認可の最終責務** は Service 側。
* **ドメイン整合**（状態遷移/上限/重複/外部キー存在）を再検証。
* 違反時は `XxxException + XxxErrorCode` を送出し、Advice で一般エラーへ統一。
* 冪等性/重複送信対策（トークン/バージョン）もここで担保。

### 3) DB（最後の柵）

* `NOT NULL` / `CHECK` / `UNIQUE` / `FK` を必ず設計。
* DB違反は Advice で **400/409** に畳む（重複登録・整合違反）。

### 4) バイパス時の扱い（フロントで止まるはずが突破された）

* **ユーザミス相当**：Controller Validator で検知 → 422/同画面。ログ: `INFO`。
* **改ざん/不正疑い**：Service/IdBridge/整合で検知 → 400/一般エラー。ログ: `WARN`（`userId, route, viewId, reason`）。
* 必要に応じて **進行中セッション（attempt 等）を安全に破棄/再生成**。

### 5) エラーメッセージの運搬

* フィールドエラー：`BindingResult`（field 単位）。
* 一般エラー：`PropKey.ERROR_MESSAGE`（flash or model）。

## 17. エラー設計・実装（認証前/後分離＋traceId短期保存｜2025-10-19追加)

* 目的：例外ハンドリングを一元化し、再読込でもメッセージが消えないよう **traceId をURLに載せて短期保持**。
* 命名/配置（my_exception｜ルートpkgは com.*）：

  * 画面DTO：`com.exception.api.ErrorViewDto`（record）
  * 状態IF：`com.exception.api.ErrorStateService`
  * 実装：`com.exception.internal.ErrorStateServiceImpl`（@Service｜TTL）
  * CSV出力：`ErrorReportService`（my_util の `MyCsvExporter` を利用）
* AppPath（全て `private final String`）：

  * `LOGIN_ERROR = "/login/error"`, `R_LOGIN_ERROR = "redirect:/login/error"`
  * `USER_ERROR = "/user/error"`, `R_USER_ERROR = "redirect:/user/error"`
  * `ADMIN_USER = "/admin/user"`, `R_ADMIN_USER = "redirect:/admin/user"`
* ハンドリング（`MyRuntimeException`）：

  1. `traceId = UUID` 発行 → `logger.error("[{}] {} {}", traceId, errorCode, ex.getMessage(), ex)`
  2. Flash：`status/errorCode/errorMessage/traceId` ＋ Redirectに `traceId` をクエリ付与
  3. `ErrorStateService.put(traceId, new ErrorViewDto(...))` 短期保持
  4. リダイレクト：未認証→`R_LOGIN_ERROR`／認証後→**権限分岐**（`ROLE_ADMIN`→`R_ADMIN_USER`／その他→`R_USER_ERROR`）
* 表示：`/login/error`（permitAll, CSV無）／`/user/error`（認証必須, CSV保存ボタン有り）／`/admin/user` は既存管理UIで受けて表示。
* Security：`/login`, `/login/error`, `/css/**`, `/js/**`, `/img/**`, `/psfm/**` は permitAll ／ `/admin/**` は `ROLE_ADMIN`。
* **HTTPステータス**：`ErrorCode` は **`com.exception.error_code.HttpStatusCode`** を返却/受理する（Spring 非依存の軽量 enum）。Advice はこれを基に `status` を決定する。

## 18. キャッシュ＆セッション運用（2025-10-18追加）

* SSOT：**userId 不変／username 可変**。`Principal` に userId を必ず含める。
* 自分のユーザー名変更：ログイン維持→**SecurityContext の principal を即差し替え**→`UserCache` 等の **旧 username を evict**。
* 自分のパスワードリセット：**必ずログアウト**（セッション破棄＋必要なら Remember-Me 無効）。
* 管理者が他人を変更：**旧 username を evict** のみ。セッションは維持（反映は次回ログイン）。
* アプリ @Cacheable：username キーは変更直後に evict／ID キーは原則不要。JPA は **コミット後に再取得**。
* 表示：画面は「userId 固定 + username 可変」。`Authentication#getName()` 直参照は避けるか principal 差し替え後に使用。

## 20. my_util での Spring 利用（ユーティリティ層方針｜2025-10-19追加）

* 位置づけ：**JARライブラリ**として維持し、**Spring Boot化しない**（`@SpringBootApplication` は置かない）。
* アノテーション：`@Component`／`@PersistenceContext`／`@Transactional` 等の **Spring/JPAアノテーションは利用可**。
* 依存関係：`spring-context`／`spring-orm`／`spring-tx`／`jakarta.persistence-api`／`jakarta.transaction-api` は **provided**（暫定で compile も可）。
* Bean登録：親アプリの `scanBasePackages` に **`"com.util"`** を含めて検出。

## 32. コーディング規約（最終）

### 32.1 Java（数値基準）

* 1行最大文字数：100／1ファイル行数目安：1,000（超過時は分割検討）
* 1メソッド行数上限：80（目安40）／条件ネスト深さ：2まで（3段目はガード節）
* 循環的複雑度：10以下／`@Override`：必須
* マジック値禁止（0/1/-1/""/emptyのみ例外）
* `static` は純関数のみ（状態保持禁止）
* `Serializable` は必要時のみ。`serialVersionUID` を明示
* コメント：Javadoc必須（要約/@param/@return/@throws）。**意図**を書く

### 32.2 Repository 方針（実装クラス排除）

* `JpaRepository` + `JpaSpecificationExecutor` を既定
* クエリは導出メソッドを基本。SQL/JPQL直書きは最小限
* 付加ロジックは Repository インターフェースの `default` メソッドでラップ
* DBデフォルト値活用：

  * Entityに `@DynamicInsert`（null列をINSERTから除外）
  * デフォルト列は `insertable=false, updatable=false` でDBに委任
  * `@Generated(GenerationTime.INSERT)` or save後に `refresh/find` で読み戻す
* `messageSource` は i18n専用。SQL/ロジックは格納しない

### 32.3 非同期/排他

* 既定は同期。必要時のみ `@Async` + 専用 Executor
* 一意/FK制約で整合確保。必要に応じ `advisory_xact_lock` を使用

### 32.4 フロント/プロパティ

* UTF-8固定、出力はエスケープ（`th:text` 既定、`th:utext` 禁止）
* JSは JSDoc 必須。DOM契約（必須class/data-属性）を先頭に明記
* properties は UTF-8。Key は `label.` / `error.` / `regex.` / `app.` / `security.`
* `PropKey` は final クラスで集中管理（windowへの一括積みもこちら経由）

### 32.5 Eclipse 運用

* Code Templates で Javadoc 雛形を設定

* Save Actions：Format / Organize imports / Add missing `@Override` を ON

* Code Templates：`/.eclipse/templates/codetemplates.xml` を VCS 管理し、Eclipse の Code Templates に Import。ファイル／型／フィールド／メソッド／@Override のコメントはテンプレート由来とする。

* テンプレ更新時はリポジトリの XML を唯一ソース（SSOT）とし、各端末での手編集は禁止。

## 33. テスト設計（JUnit）｜2025-10-23追加

### 33.1 レイヤと使い分け

* **Unit（最優先）**：Spring起動なし。純ロジック／文字列系／PropKey⇔properties／正規表現の構文・挙動。
* **Slice**：`@WebMvcTest` / `@DataJpaTest` 等。層を限定して起動（MVCのみ・JPAのみなど）。
* **Integration**：`@SpringBootTest`。**アプリ起動が必要な経路のみ**。件数は最小に。

### 33.2 配置・パッケージ

* 基本：**本体と同一パッケージ階層**にミラー配置（`package-private` に触れられて見通しが良い）。
* `@SpringBootTest`：アプリのルート（例：`com.javastudy`）配下に置くか、`@SpringBootTest(classes = <エントリ>)` を**必ず明示**。

### 33.3 命名・書き方

* クラス名：`XxxTest`
* メソッド名：**挙動が分かる日本語OK**（例：`username_OKとNGの代表例()`／`～であること()`）
* **1テスト=1責務**（存在／構文／挙動などに分割）
* 失敗メッセージは**修正指示になる文面**に

### 33.4 タグ運用（推奨）

* 契約系（PropKey/regex/DB）：`@Tag("contract")`
* 統合：`@Tag("integration")`
* 実行例：`mvn -q -Djunit.jupiter.tags.include=contract test`

### 33.5 テスト資源（properties 等）

* 置き場：`src/test/resources`（推奨）または `src/main/resources` のクラスパス直下
* 複数階層に置く場合は、テスト側で `classpath*:**/<name>.properties` のワイルドカード探索を許容

## 34. ログ設計（基本規則）｜2025-10-23追加

### 34.1 目的と原則

* 目的：障害解析・利用状況把握・性能監視のために、**最小十分**なログを一貫形式で残す。
* 原則：

  * 画面に見せる情報（UI）と**ログ専用の内部情報**を分離。
  * **相関ID（viewId）**で全レイヤのログをひとつなぎにする。
  * PII/秘匿情報は出さない（ユーザー名などは原則IDのみ、本文・入力値は不可）。
  * ログ文字列は **`private static final String`** の定数で管理。
  * クラスは AOP方針により **public 非final**。DTO は **record**。

### 34.2 配置と責務分離（ハイブリッド）

* **共通（基盤）**：`com.javastudy.config.logging`

  * 例外集約、Validation/HTTPエラー集約、性能AOP、MDC伝播、起動ログ、認証系ハンドラなど。
* **各コンポーネント internal**：

  * 画面/機能の**業務イベント（何が起きたか）**を最短で出す。
  * Repository は**原則ログなし**（件数等は Service 層で）。

### 34.3 相関ID（viewId）

* 取得順：`X-View-Id` ヘッダ → `viewId` クエリ/フォーム → **無ければ UUID**払い出し。
* MDC キー：`viewId`（**全ログに自動付帯**）。
* 適用：`ViewIdInterceptor` を MVC に登録。非同期は `MdcTaskDecorator` で継承。
* ID方針：ID は基本 **viewId** を用いる。

### 34.4 レベル指針（層別）

* Controller：ユーザー操作の主要イベント＝**INFO**（ID/件数/状態のみ）。
* ControllerAdvice：**ERROR/WARN** のみ（例外は Global に集約）。
* Service：書き込み＝**INFO**（生成ID・件数）、読み取り＝**DEBUG**（件数・範囲）。
* Repository：**原則ログ無し**。
* Validator：想定内 NG は **DEBUG**（大量発生回避）。
* Security：認証成功＝**INFO**、失敗＝**WARN**、ログアウト＝**INFO**。
* 性能：しきい値超過を **WARN**。

### 34.5 例外ハンドリング（業務系）

* クラス：`GlobalAppExceptionAdvice`
* 入力：`MyRuntimeException`
* 出力：UI向け `status/code/message/traceId` を **Flash + Query(traceId)** で PRG。
* 短期保存：`ErrorStateService` に `traceId` をキー保存（エラー画面で復元）。
* 遷移規則：

  * `/login/**` は常に **`R_LOGIN_ERROR`**（認証があれば安全にログアウト）。
  * それ以外は **権限で分岐**：`ROLE_ADMIN` → **`R_ADMIN_ERROR`**、それ以外 → **`R_USER_ERROR`**。

    * ※ 本章の遷移規則は最新・優先。
* ログ：`EX_HANDLED code={} status={} traceId={} viewId={}` を **ERROR** で出力。
* 画面には内部構造（スタックトレース等）を出さない。

### 34.6 入力検証・HTTPエラーの集約

* **Validation**：`GlobalValidationAdvice`

  * `BindException` / `MethodArgumentNotValidException` を **WARN 要約**。
  * 件数＋先頭3件（`field:code`）のみ記録 → 画面は共通メッセージへ。
  * 遷移先は 34.5 と同じ規則（`/login` or 権限）。
* **HTTP系**：`GlobalHttpErrorAdvice`

  * `404/405` を **WARN** で記録（`NOT_FOUND`/`METHOD_NOT_ALLOWED`）→ 同規則で遷移。

### 34.7 性能監視（AOP）

* クラス：`ServicePerfAspect`
* 対象：`@Service` メソッド。
* しきい値：**500ms 超**で `SLOW_SERVICE class={} method={} ms={} viewId={}` を **WARN**。
* しきい値は**コード定数**（必要に応じてプロパティ化可）。

### 34.8 認証イベント

* 成功：`AuthSuccessHandler` → `LOGIN_SUCCESS user={} roles={} viewId={}`（INFO）
* 失敗：`AuthFailureHandler` → `LOGIN_FAIL username={} reason={} viewId={}`（WARN）
* ログアウト：`LogoutSuccessHandlerImpl` → `LOGOUT user={} viewId={}`（INFO）

### 34.9 メッセージ/出力ルール

* **必須項目**：常に `viewId` を含める。例外時は `traceId` を発番しログに含める。
* **記録値**：**ID と件数に限定**。自由入力値・本文・機微情報は記録不可。
* **定数**：ログメッセージは `private static final String` で管理。
* **形式**：`KEY value1={} value2={}` の定型。
* **国際化**：画面メッセージは `ValidationMessageUtil/*.properties` を介す。**ログは英語の短句＋key**。

### 34.10 起動時ログ

* クラス：`BootLogging`
* 起動完了時に `APP_READY app={} profiles={} pid={} jvm={} dbUrl={}` を **INFO**。

### 34.11 非同期・バッチ

* MDC継承：`ThreadPoolTaskExecutor` に `MdcTaskDecorator` を設定。
* バッチ処理も同様に `viewId` を付与（無ければ起動時に UUID払い出し）。

### 34.12 テスト観点（抜粋）

* `/login/**` の例外が **必ず `R_LOGIN_ERROR`** へ遷移すること。
* 管理者セッションでの例外が **`R_ADMIN_ERROR`**、一般は **`R_USER_ERROR`**。
* `@Service` の **500ms 超**で `SLOW_SERVICE` が出ること。
* Validation 異常で **WARN が1行**、画面に機微情報が出ないこと。
* ログ各行に **viewId** が含まれること。

### 34.13 付録：担当クラス一覧（共通）

* `config.logging.advice`：`GlobalAppExceptionAdvice` / `GlobalValidationAdvice` / `GlobalHttpErrorAdvice` / `GlobalValidationMessagesAdvice`
* `config.logging.web`：`ViewIdInterceptor` / `LoggingWebConfig`
* `config.logging.aop`：`ServicePerfAspect`
* `config.logging.async`：`MdcTaskDecorator`
* `config.logging.boot`：`BootLogging`
* `config.logging.security`：`AuthSuccessHandler` / `AuthFailureHandler` / `LogoutSuccessHandlerImpl`
